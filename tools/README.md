# Porting tools

These exist to compare the PDF renderer in `internal/service/pdf` against the
Node implementation in [hebcal-web](https://github.com/hebcal/hebcal-web). They
live here rather than there because they are artifacts of the port: hebcal-web
has no use for them, and every one of them was written to answer a question
about whether this service matches it.

They are not part of the build. Nothing in `*.go` imports them, and the service
does not need Node or Python to run.

## Why they need hebcal-web

The `.mjs` tools import `pdfkit`, `@hebcal/core` and `dayjs` out of hebcal-web's
`node_modules`, because the point is to measure the reference implementation
rather than a second copy of it that might drift. They expect a hebcal-web
checkout with its dependencies installed:

```sh
git clone https://github.com/hebcal/hebcal-web ../hebcal-web
cd ../hebcal-web && npm install
```

They look for it at `../hebcal-web`; set `HEBCAL_WEB` if it lives elsewhere.
Node resolves bare specifiers relative to the importing file, so a tool in this
directory cannot simply `import 'pdfkit'` even when run from hebcal-web —
`hebcalweb.mjs` builds absolute file URLs to work around that, and everything
else goes through it.

## compare-pdfs.py

Compares two renderings of the same calendar, word position by word position.
Needs poppler (`brew install poppler`).

```sh
tools/compare-pdfs.py production.pdf mine.pdf --links
tools/compare-pdfs.py production.pdf mine.pdf --latin-only
```

This is the one that found the layout bugs. `worst dx` is the number to watch:
horizontal position comes from text measurement, so a systematic dx means the
shaper disagrees with pdfkit. That is how the pixel-grid quantisation surfaced —
as a worst dx of 1.96pt that fell to 0.11pt once runs were shaped at a reference
size and scaled.

`--latin-only` is not a shortcut. pdftotext segments Hebrew differently in the
two documents: hebcal-web draws it through `reverseHebrewWords()`, which leaves
combining marks split from their letters, so the same line extracts as a
different set of "words" and a direct comparison reports differences that are
not there. The Latin and numeric text — day numbers, times, years — is laid out
by the same code, so comparing only that is both honest and sufficient.

## fetch-both.sh

Fetches the same URLs from the Node and Go services into one folder, named
`<basename>-js.pdf` and `<basename>-go.pdf`, for side-by-side viewing.

```sh
tail -1200 /var/log/hebcal/access.log | grep pdf | jq .url | tools/fetch-both.sh
tools/fetch-both.sh -o /tmp/cmp -j 8080 -g 8082 urls.txt
```

Input is one URL or path per line, tolerating `jq`'s quotes, so an access log
can be piped straight in. Only curl is required; with poppler installed the
summary also compares page counts and flags mismatches.

Sampling real traffic this way is worth more than re-checking the same few
calendars: the first ten URLs taken from a production log turned up the
alternate-date rendering bug, which none of the hand-picked test calendars
exercised because none of them set `d=on`.

## measure-widths.mjs

Prints pdfkit's text measurements, which are the reference values pinned in
`internal/service/pdf/width_parity_test.go`.

```sh
node tools/measure-widths.mjs
node tools/measure-widths.mjs hebrew 12 'פרשת ויחי'
```

Two things make it worth having. pdfkit draws Hebrew only after
`reverseHebrewWords()` has rewritten it, and that function rejoins words with
*two* spaces, so the string on the page is not the string in the event — the
width to match is the rewritten one. And advances have to be compared at the
size actually drawn: shaping at 8.5pt quantises them to the pixel grid, which is
how an 8.5pt space came out 1.797pt instead of 1.700.

## dump-locales.mjs

Regenerates `internal/model/calendarnames.go`.

```sh
node tools/dump-locales.mjs --go > internal/model/calendarnames.go
gofmt -w internal/model/calendarnames.go
```

hebcal-web takes its month and weekday names from the dayjs locales that
`src/dayjs-locales.js` imports. Generating from the same source is what keeps a
German or Portuguese calendar reading identically in both implementations,
rather than a hand-typed table that drifts. Re-run it if hebcal-web adds a
locale to `localeMap` in `src/lang.js`.

## dump-urls.mjs

Dumps every event and its canonical URL from `@hebcal/core`, for diffing against
the same range generated by hebcal-go.

```sh
node tools/dump-urls.mjs diaspora > /tmp/js-d.tsv
node tools/dump-urls.mjs il       > /tmp/js-i.tsv
```

Running this over 1990–2089 on both schedules found three URL bugs that a single
year did not: Yom Kippur Katan has no page at all, a common year's single Adar
must not be numbered `adar-i`, and Erev Pesach and Erev Sukkot were missing the
`IL_ONLY`/`CHUL_ONLY` flags that decide whether a link carries `?i=on`. Those
fixes are in hebcal-go v0.19.0. The Go half of that comparison was a throwaway
`cmd/` program in hebcal-go; if the comparison is worth repeating, it is worth
rewriting there rather than keeping a copy here.

## What is not here

The remaining known divergences are recorded so nobody re-derives them:

- **Chanukah candle-lighting times differ by about a minute**, and one
  `Fast ends` time by four. Comparing all 143 timed events in 2028 found 4
  differences, so this is a zmanim question for hebcal-go and noaa-go, not a
  rendering one.
- **`Achrei Mot-Kedoshim` links fall back to the long URL form**, because
  keying on the text before the first hyphen finds `achrei`.
  `@hebcal/rest-api` has the identical quirk, so this matches production and
  should not be "fixed" into a divergence.
- **The `ft` ligature is missing from both documents' ToUnicode maps**, so
  `Shoftim` extracts oddly from either. It is a pdftotext artifact of a
  ligature neither implementation maps, not a regression.
